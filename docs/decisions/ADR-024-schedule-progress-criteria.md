# ADR-024 일정·진척률 기준, 완료 후 작업 규칙, 태스크 간소화 기준

- 상태: 승인(기획 단계 결정, 2026-11-25) — 근거: 피드백 정리 261124(팀장님 "표현 방식보다 기준 정립이 우선", "완료 후 작업 구분 기준 필요", 본부장님 "태스크가 지나치게 세분화")
- 관계: ADR-018(진척률·상태·완료일)을 구체화·보완한다.

## 1. 일정·진척 값의 정의 (서로 섞지 않는다)
| 값 | 정의 | 출처 | 화면 표기 |
|---|---|---|---|
| **계획 기간** | 계획상 시작일~마감일 | WBS, 회의록의 일정, 담당자 정정 | "계획 11/4–11/10" / 없으면 "일정 미정" / 마감만 없으면 "11/18 ~ 종료일 미정" |
| **계획 마감일** | 계획 기간의 끝 | 위와 같음 | 지연·이번 주 마감 판단에 쓴다 |
| **실제 작업 기간** | 첫 작업 내역 날짜 ~ (완료면 완료일, 아니면 마지막 작업 내역 날짜) | 작업 내역(자동) | "실제 11/11–11/13". 작업 내역이 없으면 비움 |
| **완료 여부** | 상태가 완료이고 완료일·완료 근거가 있음 | 산출물 판별(ADR-018 §4) 또는 사람 | 완료 칩 + "완료 11/13" |
| **일정 상태** | 오늘 기준 계획 대비 상태: 예정·진행 중·지연·확인 필요·완료 | 위 값의 조합(ADR-018 §6) | 상태 칩 |
| **기한 준수** | 완료일 ≤ 계획 마감일이면 기한 내, 아니면 기한 후 | 완료일·계획 마감일 | 완료 칩 옆 "기한 후 2일"(기한 후일 때만) |
| **태스크 진척** | 완료/미완료 둘뿐. 부분 %는 쓰지 않는다 | — | — |
| **프로젝트 진척률** | 완료 태스크 수 ÷ 전체 태스크 수(합쳐진 태스크 제외) | 자동 | "진척 75% · 6/8" |
| **계획 진도** | 계획 마감일이 있는 태스크 중 마감일이 지난 비율(확인 필요 제외) | 자동 | 진척률이 더 낮으면 "계획보다 늦음" |
| **단계 진행** | 단계별: 모든 태스크 완료=완료, 진행 중 있음=진행, 아직=예정 | stage + 상태 | 단계 칩 |

- 간트 바는 계획 기간, 점은 실제로 작업한 날(지금 방식 유지). 표와 드로어에는 계획 기간·실제 작업 기간·완료일을 **각각의 칸**으로 둔다.
- 계획이 바뀌면(마감 연기) 새 계획 마감일로 판단하고, 이전 마감일은 이력으로 남긴다.

## 2. 완료 후 작업 규칙
완료된 태스크에 수정·업로드가 생기면 아래 순서로 판단한다.

| 경우 | 판단 기준 | 처리 |
|---|---|---|
| **A. 완료 후 보완** | 같은 산출물(같은 파일·같은 문서의 판 갱신)을 다듬은 것: 오탈자·서식, 피드백 일부 반영, 최종본 업로드, 공유용 정리. 완료일로부터 14일 이내 | 기존 태스크의 작업 내역으로 붙이고 **완료 유지**, 완료일 그대로. 작업 내역에 "완료 후 보완" 표시. 실제 작업 기간은 늘리지 않는다 |
| **B. 재작업(연장)** | 같은 산출물이지만 검토 결과 다시 만들어야 하는 수준: 구조·결론이 바뀜, "다시 정리해 달라"는 요청, 완료 판단이 틀렸음 | 태스크를 **진행 중으로 되돌리고** 완료일을 지운다. 사유를 이력에 남긴다. 다시 끝나면 새 완료일 |
| **C. 새 태스크** | 새 산출물·새 목적·다음 차수(2차 리뷰, 다음 달 보고서, 다음 단계 작업), 또는 완료 후 14일이 지난 같은 산출물의 큰 변경 | **새 태스크**를 만들고 이전 태스크와 연결("이어지는 태스크") |
| 애매함 | 위 셋 중 판단 근거가 부족 | A로 붙이되 판단 보류로 남긴다 |

- 사례(2026-11-25 데이터): 1팀·3팀 업무 프로세스 인터뷰(완료 후 결과서 판 갱신) → A. ai-automate 2차 리서치(완료 후 비교표 수정·추가 리뷰) → 내용이 확장되면 C.
- 사람이 화면에서 A/B/C를 바꾸면 그 판단을 따르고, 이후 같은 태스크의 자동 판별 기준으로 쓴다.

## 3. 태스크 간소화 기준
본부장님 피드백: 태스크가 지나치게 세분화되어 가독성이 낮다.

- **태스크 = 산출물(결과물) 하나 또는 결정 하나**. 그 산출물을 만들기 위한 준비·회의·반영·검토는 태스크가 아니라 작업 내역이다.
  - 예: "이관 미팅 자료 준비 → 1차 미팅 → 피드백 반영"은 "이관 계획 확정" 한 태스크.
  - 예: "Browser Use 점검 / Computer Use 점검 / Git OFF 검증"처럼 결과물이 다르면 따로 둔다. 다만 같은 보고서 하나로 묶이면 한 태스크.
- **차수가 이어지는 같은 성격의 일**(1차·2차·3차 기획 리뷰)은 "기획 리뷰" 한 태스크로 두고 차수는 작업 내역으로. 단, 차수마다 다른 결론·산출물이 남으면 따로 둔다.
- **WBS 행은 참고**: WBS가 잘게 나뉘어 있어도 위 기준으로 합친다. 합친 WBS 번호는 대상 태스크에 남겨 추적한다(`merged_into`).
- **목표 규모**: 핵심 프로젝트 하나의 한 단계에 태스크 3~5개 이내. 넘으면 합칠 수 있는지 다시 본다.
- 합치기는 판별 에이전트가 하고, 화면에서 사람이 되돌릴 수 있다.

## 4. 적용
- 화면: 태스크 상세 표·드로어에 계획 기간·실제 작업 기간·완료일·기한 준수 칸, 완료 후 보완 표시.
- 판별: 수집 절차서에 §2·§3 규칙 추가, 기존 데이터에 1회 적용(6단계).
