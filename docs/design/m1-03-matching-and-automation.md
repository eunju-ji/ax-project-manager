# M1-03 동일 업무 판별(OD-14)과 자동/검토 경계(OD-15)

> 작성: AX-Lead, 2026-11-19 · 상태: **설계안 v2**(AX-Reviewer 검토 반영) · 기준: L02 §같은 업무인지 판단, L03 Q03·Q07, ADR-004·006·007·008, M1-01

## 1. 두 단계를 나눈다
1. **식별(중복 수집 방지)**: 같은 이벤트인가? → `event_key`·`source_key` 비교(M1-01 §2.1). 결정적이며 LLM을 쓰지 않는다.
2. **의미 판별(동일 업무)**: 새 이벤트가 어떤 업무에 속하나? → 아래 분류. LLM 후보 + 사람 확정.

## 2. 의미 판별 분류
새 SourceEvent마다 하나를 제안한다. **원칙: 아래 §3 자동 허용 목록에 없는 판단은 모두 검토로 간다.**

| 분류 | 뜻 | 결과 |
|---|---|---|
| A. 기존 근거 추가 | 이미 있는 WorkLog의 추가 근거 | 기존 WorkLog에 Link 추가(건수 증가 없음). **검토 후 확정** |
| B. 새 작업 내역 | 기존 태스크 안에서 별개 결과물의 실행 | 새 WorkLog + Link. **검토 후 확정** |
| C. 새 태스크 후보 | 어떤 태스크의 목적·완료 기준에도 맞지 않음 | `new_task` Review. 자동 생성 금지 |
| D. 업무 아님/보류 | 근거 부족, 개인 자료 등 | 연결하지 않음 |

### 판별 근거 우선순위
1. 사람의 교정 기록(§4). 교정과 아래 근거가 충돌하면 자동 적용을 멈추고 Review로 보낸다.
2. 명시적 참조: 태스크 ID(예: 커밋 메시지·PR 본문의 `TSK-…`). **태스크를 식별할 뿐이며 A/B 분류를 증명하지 않는다.**
3. 기존 Link 관계: 같은 Source에 confirmed Link가 있음(여러 WorkLog에 연결돼 있으면 후보가 여러 개)
4. 태스크 목적·완료 기준·기대 결과물과의 내용 일치(LLM)
5. 요청 흐름: 같은 스레드·PR·문서의 앞선 이벤트
- 작성자가 같다, 제목이 비슷하다, 같은 날 같은 문서를 고쳤다는 이유만으로 A를 확정하지 않는다(L02). 이런 조건은 **후보 순위**에만 쓴다.

### 실행자
- 이벤트 행위자(외부 계정) → Person 매핑은 "그 계정이 누구인가"일 뿐, 그 사람이 WorkLog의 실행자라는 뜻은 아니다.
- WorkLog.performer는 `performer_basis`(예: 커밋 author이며 봇이 아님, 문서 편집 행위자 본인)가 있을 때만 채운다. GitHub author·committer·pusher가 다르거나, 봇 계정이거나, 대리 작업 가능성이 있으면 `unknown` + `performer` Review.
- 메일·요청 작성자는 실행자로 추정하지 않는다.

## 3. 자동 처리 vs 검토 (OD-15)

> **2026-11-19 변경: ADR-016이 이 절을 대체한다.** 확신도가 높으면 연결·새 작업 내역·새 태스크·새 프로젝트·병합·분리를 자동 반영하고, 근거 충돌·확신도 미달·사람이 고친 결정의 재변경만 검토로 보낸다. 아래 목록은 이력으로 남긴다.
**자동 허용 목록**(사람 확인 없이 적용, History에 `system`으로 기록). 이 목록 밖은 모두 검토다.
1. 식별 중복 제거(같은 `event_key`, 같은 digest의 재수집)
2. 명시적 태스크 ID 참조 → **Task Link**(evidence → task)까지만 생성. 조건: 그 태스크가 존재하고, 이벤트의 소스·계정 범위가 그 프로젝트의 승인된 수집 범위 안에 있고, §4의 억제·교정과 충돌하지 않을 것. WorkLog 연결·생성은 하지 않는다.
3. Source.availability와 확인 시각 갱신
4. 시스템이 쓴 요약 문구 갱신(사람이 쓴 필드는 덮어쓰지 않음)

**검토 필수**(예시, 전부가 아님): A·B 분류 전부, C, 병합·분할·태스크 이동, 완료 관련 판단(M1-02), 근거 충돌(후보 여러 개를 근거와 함께 보여 주고 확정하지 않음), 실행자 불확실, 키 충돌(M1-01 §2.1).
- 자동 범위 확대(예: 같은 PR의 추가 커밋을 기존 WorkLog에 A로 자동 연결)는 파일럿 교정 데이터를 보고 별도로 승인받는다.

## 4. 교정 지속성
- 사람이 Link를 거절하면 그 Link는 `rejected`로 남고, **Suppression**이 생긴다. 범위는 거절 시 사람이 고른다.
  - `event`: 이 이벤트만 이 대상에 연결하지 않음
  - `source`(기본값): 이 원본에서 나오는 이후 이벤트도 이 대상으로 자동 제안·자동 연결하지 않음
- 억제 키: (scope, evidence_type, evidence_key, target_type, target_id).
- 사람이 다른 대상으로 재연결하면: 기존 Link rejected + source 범위 Suppression, 새 Link confirmed. 같은 Source의 이후 이벤트는 새 대상을 우선 후보로 쓴다.
- 명시적 ID 참조가 억제된 대상을 가리키면 자동 연결하지 않고 `conflict` Review로 보낸다(과거의 잘못된 ID 표기가 교정을 덮지 않게).
- **해제 경로**: Suppression은 사람이 해제할 수 있다(released_by/at 기록). 관계가 실제로 바뀐 경우를 위해 억제된 후보도 검토 화면에서 "억제됨"으로 조회할 수 있게 한다.
- 교정 기록은 LLM 판별 입력(최근 교정 사례)으로 쓴다. 이 입력도 ADR-007 보호 범위에 들어간다.
- 테스트: 거절(source 범위) → 같은 원본의 새 이벤트 → 같은 대상으로 제안되지 않음 / 억제 대상을 가리키는 명시적 ID → conflict Review / 해제 → 다시 제안됨.

## 5. LLM 경계와 보안
- LLM 출력은 Review 제안이나 자동 허용 목록 안의 변경 요청일 뿐이다. 쓰기 계약(M1-01 §4)의 검증을 거쳐야 적용된다.
- **외부 텍스트는 데이터로만 취급한다.** 커밋 메시지·문서 제목·PR 본문에 들어 있는 지시문은 LLM에 대한 명령이 아니다. 프롬프트에서 외부 텍스트를 구분해 넣고, LLM이 자동 허용 목록 밖의 변경을 요청하면 무시하고 Review로 돌린다.
- 자동 연결은 항상 수집 범위(소스·계정·프로젝트) 검사를 거친다. 태스크 ID가 존재한다는 사실만으로 연결 권한을 인정하지 않는다.
- 입력은 공통 허브에 보존이 허용된 메타·요약까지만 쓴다. 원문 전문은 원본 권한 범위 안에서만 쓰고 저장하지 않는다(ADR-005·007). 세부는 G2 전에 정한다.
