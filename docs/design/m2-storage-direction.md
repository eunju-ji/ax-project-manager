# M2 저장소 방향 검토 — Sheets 단독 운영 vs DB 원본

> 작성: AX-Lead, 2026-11-19 · 상태: **사용자 승인 대기**(중요 아키텍처 변경, AGENTS.md §9)
> 근거: `docs/migration/m2-local-report.md`(1~3회차 수정 기록, "저장소 제약 때문에 생긴 복잡성 목록"), AX-Reviewer 1·2·3회차 재검증, OD-09 전환 기준(`docs/migration/open-decisions.md`)

## 1. 결과 요약
- 로컬 PoC는 Sheets처럼 **행 하나씩만 안전하게 쓸 수 있고 여러 행을 한 번에 묶어 저장하지 못하는** 저장소 위에서 3회 수정·재검증했다. 3회 모두 fail.
- 회차별 결함 수: 1회차 high 5·medium 3·low 1 → 2회차 high 3·medium 3 → 3회차 high 1·medium 2. 줄어들고는 있다.
- 3회차에 남은 결함(“진행 중” 판단의 예약 복구 누락, 복구 결과를 “저장됨”으로 잘못 표시, 참조 검사 범위)은 **구현 결함**으로 분류됐다.
- 그러나 결함이 계속 생긴 영역은 모두 **여러 행 원자성 부재를 메우려고 만든 중간 상태·복구 절차**였다(예약 → 태스크 → 판단, 실행 목록 선기록, 이력 보충, 미완료 데이터 격리, 보정 실행). Reviewer는 3회차에 "**DB 원본 + Sheets 조회용 우선 검토**"를 권고했다.

## 2. 사용자 전환 기준에 비춘 판단
| 기준 | 판단 |
|---|---|
| 3회차에도 문제가 남았는가 | 예 (fail) |
| 남은 문제가 Sheets식 제약 때문인가 | 직접 원인은 구현 결함. 그러나 결함이 생긴 코드 자체가 저장소 제약을 우회하려고 만든 부분이다 |
| 결론 | **전환 검토 조건에 해당한다고 본다.** 같은 구조를 계속 고치면 복구 경로가 늘 때마다 새 결함이 생길 가능성이 높다 |

## 3. 선택지
| | (A) Sheets 단독 유지 | (B) DB 원본 + Sheets 조회용 **(권고)** | (C) DB + 웹 화면만 |
|---|---|---|---|
| 데이터 원본 | Sheets | 트랜잭션 DB | 트랜잭션 DB |
| 팀이 현황을 보는 곳 | Sheets + 화면 | 화면 + Sheets(DB에서 내보낸 읽기 전용 사본) | 화면만 |
| 여러 행 동시 저장 | 불가 → 예약·보정 절차 유지 | 한 트랜잭션으로 처리 | 한 트랜잭션으로 처리 |
| 없어지는 복잡성 | 없음 | 예약 중간 상태, 실행 목록 선기록·보정 실행, 이력 보충, 미완료 데이터 격리 대부분 | (B)와 같음 + Sheets 내보내기 |
| 그대로 필요한 것 | 전부 | 같은 요청 중복 방지, 버전 충돌, 감사 기록, 응답 유실 처리, 판정 결과 표시 | (B)와 같음 |
| legacy 원칙(P8 "공통 Sheets가 현황 보관")과의 관계 | 그대로 | "보관"은 DB, "팀 공유 현황"은 Sheets로 나눠 취지 유지 | 원칙 변경 필요 |
| 추가 부담 | 없음 | DB 운영(호스팅 결정은 비용 승인 대상), 내보내기 작업 | DB 운영, 사용자 교육 |

## 4. 권고: (B) DB 원본 + Sheets 조회용
- 팀이 Sheets로 현황을 보는 경험은 유지하면서, 결함이 반복된 영역을 DB 트랜잭션으로 없앨 수 있다.
- Sheets는 **읽기 전용 사본**이다. 사람이 Sheets를 고쳐도 원본이 바뀌지 않는다. 판단·교정은 화면에서만 한다.

## 5. 승인 시 다음 단계 (모두 G0, 비용 없음)
1. **로컬 DB PoC**: Node 내장 `node:sqlite`(추가 설치 없음, 트랜잭션·롤백 확인함)로 저장소를 바꾸고 같은 시나리오와 3회차 재현 사례를 다시 돌린다.
   - 판단·태스크·이력을 한 트랜잭션으로 묶고, 예약 중간 상태·보정 실행·미완료 격리 코드를 제거한다.
   - 남은 구현 결함(복구 결과 표시, 참조 검사)은 DB에서도 필요하므로 함께 고친다.
   - 성공 기준: 기존 테스트·화면 기준선 유지, 재현 사례 전부 통과, 제거된 코드량 보고.
2. **Sheets 내보내기 설계**: 어떤 표를 어떤 주기로 내보낼지, 보호 대상(ADR-007)을 어떻게 가릴지 정한다. 실제 Sheets 쓰기는 G1 승인 후.
3. **운영 DB 후보 조사**: 관리형 DB 후보와 비용·권한·백업을 비교한다. 결제나 생성은 별도 승인 후.

## 6. 기록할 결정 (승인 시)
- ADR-013: 데이터 원본은 트랜잭션 DB, Sheets는 조회·공유용 읽기 전용 사본. OD-09 (A) 후보 제외.
- ADR-002·004·012는 그대로 유효. P8은 "보관=DB, 공유 현황=Sheets"로 해석을 갱신.
