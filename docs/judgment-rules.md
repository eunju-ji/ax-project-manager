- 작성: AX-Lead, 2026-11-26
- 성격: 흩어진 결정(ADR)과 수집 절차서의 판별 규칙을 한 곳에 모은 **기준 문서**다. 규칙의 근거와 자세한 사연은 각 ADR에 있다. 서로 다르면 더 최근 ADR이 우선하고, 이 문서를 고친다.
- 쓰는 곳: 정기 수집 에이전트(`docs/runbooks/real-collect.md` §3), 화면 계산(`app/src/model.js`), 사람의 검토.

## 1. 프로젝트

### 1-1. 프로젝트란
하나의 목표와 결과물을 향해 **여러 날에 걸쳐 이어지는 일의 묶음**이다. WBS에 있든 없든 같다. (ADR-021 §1)

### 1-2. 새 프로젝트를 세우는 기준 — 신호 2개 이상
같은 주제로 아래 신호가 **두 가지 이상** 겹치면 프로젝트로 세운다. 하나뿐이면 기존 프로젝트의 태스크인지 먼저 본다. (ADR-021 §2)

| 신호 | 예 |
|---|---|
| 전용 작업 공간 | 로컬 작업 폴더, Paseo 워크스페이스, Git 저장소, Drive 폴더, Chat 스페이스 |
| 목표를 적은 문서 | README·기획서·회의록에 목적·범위·완료 기준 |
| 이틀 이상 이어진 작업 | 같은 주제의 커밋·AI 세션·파일 수정이 서로 다른 날 |
| 회의·지시에서 나온 과제 | "~를 구축/추진하자"로 정해진 일 |
| 계획 문서 | WBS·업무계획의 대분류(최상위 번호) |

- 작업 폴더와 그 안의 Git 저장소는 **신호 하나**로 센다. Claude Code·Codex 세션을 도구별로 따로 세지 않는다.
- 이름은 도구가 아니라 **목표**로 짓는다(예: "Paseo 작업" ✗ → "사내 지식 구축" ✓).
- 같은 목표의 작업 공간(로컬 폴더·GitHub 저장소·Drive 폴더)은 한 프로젝트로 묶고, 대응을 `state.projects_map`에 남겨 다음 판별 기준으로 쓴다.
- 담당은 실제 작업한 사람(작업 공간의 주인). AI 에이전트 세션의 수행자는 지시한 사람이다. (ADR-021 §3)
- WBS가 있으면 **최상위 번호 = 프로젝트 단위**로 기존 프로젝트에 맞춘다. (ADR-018 §1)
- 근거가 엇갈리거나 확신이 낮으면 만들지 않고 `notes`에 보류 사유를 남긴다.

### 1-3. 핵심 프로젝트(core)와 팀 운영(ops)
프로젝트마다 `kind`를 둔다. (ADR-023 §2)

| 구분 | 기준 | 예(2026-11-24 기준) |
|---|---|---|
| **핵심 프로젝트(core)** | 팀이 만들어 내는 결과물·과제가 있는 일. 단계(리서치→출시)를 밟는다 | 관리장, 현업진단, Moncoti, Pi-automate 검토, GBC AdPilot, AX OS, 사내 지식 구축 |
| **팀 운영(ops)** | 팀을 굴리기 위한 일: 채용, 이관, 교육, 주간 일정, 단건 회의·회신 관리 | AX팀 운영, 백엔드 개발자 채용, GWS 공유폴더 이관, AX 교육·Enablement |

- WBS의 단건 회의·회신 관리 항목은 `AX팀 운영`에 넣는다. (ADR-018 §1)
- 새 프로젝트의 `kind`는 판별 에이전트가 위 기준으로 정하고, `project_updates.kind`로 바꿀 수 있다.
- 교육을 운영으로 볼지는 사용자 확인 대기 항목이었다(현재 ops).

## 2. 태스크

### 2-1. 태스크란 — "끝낼 수 있는 일"
목표·결과물(또는 완료 상태)이 있고, 누가 해야 하는지 말할 수 있는 일. (ADR-018 §8)
- **태스크 = 산출물 하나 또는 결정 하나.** 그것을 만들기 위한 준비·회의·반영·검토는 태스크가 아니라 작업 내역이다. (ADR-024 §3)
- 태스크인지 아닌지는 **WBS로 가르지 않는다.** WBS가 없는 태스크도 똑같은 태스크이고, 화면에서 "계획 외" 같은 구분을 하지 않는다. (ADR-018 §1 정정)
- 애매하면 **"이 일이 끝났다고 말할 수 있는가"**로 가른다.

### 2-2. 태스크가 아닌 것 (기록하지 않음)
- 정보·사례·도구 공유(같이 보자는 내용)
- 정기 기록: 업무일지·주간보고·개인 체크리스트
- 계획 문서 갱신 그 자체: WBS·업무계획 수정(내용은 다른 태스크 판별에 읽기만)
- 회의 일정 조율·초대·채널 운영, 인사·안내
- 참고 자료 모으기
- 별도 묶음("참고 기록" 등)도 만들지 않는다. (ADR-018 §8)

### 2-3. 태스크 단위 — 합칠 것은 합친다
- 같은 목적·같은 결과물로 이어지는 일은 **한 태스크**. 한 번의 요청·메일 대응·후속 수정은 그 업무의 작업 내역이다. (ADR-018 §9)
  - 예: "이관 미팅 자료 준비 → 1차 미팅 → 피드백 반영" → "이관 계획 확정" 한 태스크.
  - 결과물이 다르면 따로: "Browser Use 점검 / Computer Use 점검 / Git OFF 검증". 단, 같은 보고서 하나로 묶이면 한 태스크.
- 차수가 이어지는 같은 성격의 일(1·2·3차 기획 리뷰)은 한 태스크, 차수는 작업 내역. 차수마다 다른 결론·산출물이 남으면 따로. (ADR-024 §3)
- **목표 규모**: 핵심 프로젝트 한 단계에 태스크 3~5개. 넘으면 합칠 수 있는지 다시 본다. (ADR-024 §3)
- WBS가 잘게 나뉘어 있어도 위 기준으로 합친다. 합친 태스크는 지우지 않고 `merged_into: <대상>`으로 남기며 화면·진척률에서 뺀다. 합쳐진 태스크에는 기록을 붙이지 않는다.
- 새 태스크를 만들기 전에 같은 프로젝트의 기존 태스크에 넣을 수 있는지 먼저 본다.

### 2-4. WBS에서 태스크 들이기 (ADR-018 §1, 절차서 §2-1)
- **말단 행**(하위 번호 없는 행)만 태스크. 상위 행은 묶음(`wbs_groups`).
- 남기는 것: `wbs_code`, 업무명, 담당, `start_date`, `due_date`, 산출물(`summary`·`completion_criteria`), `plan_source:"wbs"`, `plan_ref`.
- 업무명·담당·날짜가 바뀐 행 → `task_updates`. 사라진 행은 지우지 않고 `notes`.
- 공동 담당 행은 실제 작업이 보이는 사람을 담당으로.

### 2-5. 태스크에 붙이는 속성
| 속성 | 기준 | 근거 |
|---|---|---|
| `description` | 무슨 업무인지 한두 문장(200자 이하), 개발 용어 없이 | 절차서 §2-1 |
| `category`(업무 유형) | 5종 중 하나: 기획·설계 / 조사·분석 / 제작·구현 / 검증 / 운영·지원. WBS의 '업무 카테고리'는 업무 유형이 아님 | ADR-018 §9 |
| `stage`(단계) | 태스크 성격으로 판별 에이전트가 정함: 리서치 · 기획 · 프로토타입 · 개발·테스트 · 출시·운영 | ADR-023 §2 |
| 담당(`assignee_id`) | 실제 작업이 보이는 사람 | ADR-018 |

**단계 판단 기준**(판별 에이전트용, 2026-11-26 이 문서에서 처음 표로 정리 — ADR-023에는 단계 이름만 있음):
| 단계 | 이런 일 |
|---|---|
| 리서치 | 조사·인터뷰·사례 분석·도구 검토·벤치마크 |
| 기획 | 목표·범위·요구사항 정리, 기획서·설계안·배치안, 계획 확정 |
| 프로토타입 | 시안·와이어프레임·PoC·시험 구현 |
| 개발·테스트 | 실제 구현, 시험·검증·QA |
| 출시·운영 | 공개·배포·이관 실행, 운영·모니터링·교육 |

## 3. 작업 내역

### 3-1. 작업 내역이 되는 것
**무언가를 만들거나, 분석·검토·결정했거나, 문제를 해결한 기록**만. (ADR-018 §10)

### 3-2. 작업 내역이 아닌 것 (delta에 넣지 않음)
- 파일 이동·폴더 구성·이름 변경·삭제·형식 전환·사본 정리
- 남의 자료·참고 자료 올리기·전달, 같은 자료 재공유, 링크만 공유
- 회의 초대·일정 변경·취소·회의실·참석 조정·채팅방 초대
- "~하겠다", "~해 달라", "~했다고 전함"처럼 의사 표시·진행 상황 전달만 있는 연락
- 이미 들어간 것은 `worklog_removals`, 작업 내역이 모두 빠지는 태스크는 `task_removals`.

### 3-3. 어느 태스크에 붙이나 (절차서 §3)
1. 먼저 **계획 태스크(WBS)**와 대조: 업무명·산출물·담당·기간. 맞으면 거기에. 이미 다른 태스크에 붙은 기록이 WBS 태스크에 더 맞으면 `worklog_updates`로 옮김.
2. 기존 태스크와 대조: 프로젝트·태스크 이름, 폴더 경로, 파일 이름, 참여자, 시기, 명시적 참조(태스크 ID·이슈·PR·파일 링크·메일 스레드). 같은 업무면 기존 태스크에(교차 소스 연결).
3. 안 맞으면 새 태스크, 프로젝트도 안 맞으면 새 프로젝트(1-2 기준). 확신이 낮으면 `notes`에 보류.
- GitHub: 같은 PR의 커밋은 한 작업 내역, PR이 없으면 하루·브랜치 단위로 묶음. 병합 커밋·버전 올리기·서식만 바꾼 커밋은 제외. (ADR-020)
- AI 대화: 제목·작업 폴더·수정 파일로 기존 태스크와 맞는 대화만. 수행자는 지시한 사람. (ADR-020, ADR-021 §3)

### 3-4. 쓰는 방식
- 제목·요약은 **개발 용어 없이 팀 밖 사람도 알아들을 말**로. 예: "서버 핵심·연결부 분리" → "관리장을 다른 무료 서버에도 올릴 수 있게 구조를 정리". (절차서 §3)
- 수행 시각은 한국 시간 기준 날짜로 집계.
- 사람 이름은 Google 표시 이름 그대로(추측 번역 금지). (ADR-017)

## 4. 상태·완료·일정

### 4-1. 완료 판별 — 근거가 분명하면 자동 완료 (ADR-016 §5, ADR-018 §4)
순서대로 본다.
1. WBS 상태 칸 `완료`.
2. **산출물 확인**: 산출물과 맞는 파일·첨부를 찾아 내용을 읽고, 양식만 있는 빈 파일이 아니라 결과가 채워졌으면 완료. 초안이면 진행 중.
3. 최종본·배포본·릴리스 공개, 완료·결정 메시지, 결과 보고서, 다음 단계 착수.
- **근거가 아닌 것**: 파일 수정만, 회의 초대만, 이름에 "최종"만, 활동이 끊겼을 뿐.
- 완료 시 `completion_basis`(무엇을 보고 판단했는지)를 남긴다.

### 4-2. 완료일 (ADR-018 §5)
| 근거 | 완료일 |
|---|---|
| 산출물 | 결과를 갖춘 정리본이 만들어진 작업 내역 시각 |
| 공개·완료 메시지 | 그 시각 |
| 다음 단계 착수 | 이 태스크의 **마지막 작업 내역** 시각 |
| WBS 완료 표시만 | 상태가 바뀐 날(이력이 있으면), 없으면 WBS 종료일 |

### 4-3. 완료 후에 수정·업로드가 생기면 (ADR-024 §2)
| 경우 | 기준 | 처리 |
|---|---|---|
| A. 완료 후 보완 | 같은 산출물 다듬기(오탈자·서식·피드백 일부·최종본 업로드), 완료 후 14일 이내 | 기존 태스크 작업 내역으로, **완료 유지** |
| B. 재작업 | 같은 산출물이지만 구조·결론이 바뀜, "다시 정리해 달라" | **진행 중으로 되돌림**, 완료일 지움 |
| C. 새 태스크 | 새 산출물·다음 차수, 또는 14일 지난 큰 변경 | 새 태스크 + 이전 태스크와 연결 |
| 애매함 | 근거 부족 | A로 붙이고 보류 |

### 4-4. 계획 날짜 (ADR-024 §1, ADR-026 §2)
- 출처: **WBS 일정**(시작·마감), **회의록·요청의 "~까지"**(마감, `due_basis`). 그 밖에는 비워 둔다.
- 계획이 바뀌면 새 마감으로 판단하고 이전 마감은 이력으로.

### 4-5. 화면 상태 (ADR-018 §1·§6, `model.js taskState`)
| 상태 | 조건 |
|---|---|
| 완료 | 저장 상태가 완료 |
| 지연 | 마감이 지났고 미완료이며 **작업 내역이 있음** |
| 확인 필요 | 마감이 지났고 미완료이며 **작업 내역도 완료 근거도 없음** |
| 진행 중 | 시작일이 지났거나(시작일 없으면 마감만 있는 경우) 진행 |
| 예정 | 시작일 전 |
| 일정 미정 | 날짜가 하나도 없음 |

### 4-6. 진척 (ADR-024 §1)
- **프로젝트 진척률** = 완료 태스크 ÷ 전체 태스크(합쳐진 태스크 제외). 태스크 단위는 완료/미완료 둘뿐.
- **실제 작업 기간** = 첫 작업 내역 ~ (완료면 완료일, 아니면 마지막 작업 내역).
- **기한 준수** = 완료일 ≤ 계획 마감이면 기한 내.
- **단계 진행** = 단계의 태스크가 모두 완료면 완료, 진행 중이 있으면 진행, 아니면 예정.

### 4-7. 간트 표시 (ADR-026 §2)
- 실선 막대 = 계획 기간, 점선 막대 = 계획이 없을 때 실제 작업 기간, ◆ = 마감만 있음, 점 = 작업한 날.
- 시작일만 있으면 오늘까지(완료면 완료일까지), 마감 < 시작이면 "일정 확인 필요".
- 프로젝트 막대 = 태스크 막대들의 범위(대체값은 작업 내역 날짜만).

## 6. 참여자·자료·제외

- **참여자**: GWS를 연동한 사람 + 공유 드라이브·Chat·메일에서 업무가 보이는 사람. 표시 이름 그대로. (ADR-017)
- **자료**: 파일만(Drive 파일, Chat·Gmail 첨부, 메시지에 공유된 파일 링크). 메시지·메일 본문은 근거(`kind:"message"`)로만. (절차서 §3)
- **제외**: Chat 1:1, `state.excluded`(제외 프로젝트·사람·스페이스), 자격 증명·키가 보이는 메시지. 제외 대상은 delta에서 거부된다. (ADR-020 §4)

## 7. 사람에게 넘기는 것 (ADR-016 §3)
- 근거가 서로 반대로 가리킴(폴더는 A, 파일 이름·참여자는 B)
- 확신도가 기준 미만
- 사람이 고친 결정을 다시 바꾸려 함
- 실행자를 특정할 수 없고 집계 영향이 큼
→ 화면의 "검토 필요"·"확인 필요"로 보이고, 사람이 화면에서 고치면 그 값이 다음 판별의 기준이 된다.
