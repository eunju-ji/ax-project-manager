# 서비스 목적과 확정 원칙

## 해결하려는 문제

업무 요청·대화·문서·코드 변경이 여러 서비스에 흩어져 있습니다. 이를 사람이 매번 다른 관리장에 옮기고 정리해야 하면 관리 업무가 늘어납니다. 반대로 기록을 모으기만 하면 같은 일을 여러 태스크로 중복 집계하거나 누가 실제로 무엇을 했는지 놓치게 됩니다.

목표는 **기록을 업무 맥락으로 연결해 팀 전체 리소스를 파악하는 것**입니다. 단순 자료 목록이나 요약문 모음이 아니라 프로젝트별 태스크와 실제 작업 내역, 그 근거를 이어야 합니다.

## 중요하게 확정한 방향

1. **기록을 업무에 연결한다.** 메일·문서·커밋은 같은 태스크의 서로 다른 근거일 수 있습니다.
2. **사람의 중복 정리 부담을 줄인다.** 반복적인 수동 전달·분류를 사용자에게 떠넘기는 것이 목표가 아닙니다. 자동 수집 범위가 검증되지 않은 부분은 해결됐다고 꾸미지 않습니다.
3. **기존 업무의 정체성을 유지한다.** 새 기록이 들어와도 기존 프로젝트·태스크 ID와 연결 관계가 유지되어야 합니다.
4. **근거를 따라갈 수 있어야 한다.** 누구의 어떤 기록에서 언제 확인했고 왜 연결·수정했는지 추적 가능해야 합니다.
5. **필요한 판단만 사람이 한다.** 불명확한 동일 업무 판별, 충돌, 중요한 변경·완료 판단에는 근거를 제시합니다.
6. **개발부터 운영까지 이어 간다.** 하나의 프로젝트에 서로 다른 성격의 태스크와 작업 내역이 계속 쌓일 수 있습니다.
7. **원본과 권한을 존중한다.** 공통 현황을 보는 권한과 원본 세부 내용을 읽는 권한은 다릅니다.
8. **시스템을 불필요하게 키우지 않는다.** 기본 방향은 LLM이 이해·판단하고 공통 Sheets가 현황을 보관하며 화면이 조회·검토를 제공하는 것입니다. 연결 지원이 안 되는 부분을 숨은 기능이나 무리한 우회로 메우지 않습니다.

## 정보 단위

| 용어 | 의미 |
|---|---|
| 프로젝트 | 하나의 과업 전체. 개발·개선·운영 내역을 계속 연결 |
| 태스크 | 프로젝트를 구성하는 구체적인 작업 |
| 작업 내역 | 한 결과 또는 작업물 단위의 세부 실행 기록. 누가 언제 무엇을 했는지 표시 |
| 관련 자료 | 업무를 뒷받침하는 원본 문서·파일·저장소·기록 |

공통 업무 유형은 **기획·설계 / 조사·분석 / 제작·구현 / 검증 / 운영·지원**이며 태스크를 묶는 기준입니다. 단계 순서가 아니고, 같은 프로젝트에서 함께 사용합니다.

## 무엇을 별도로 확인해야 하는가

위 원칙이 확정됐다고 해서 데이터 수집 경로·저장 구조·커넥터 쓰기·자동 실행이 해결된 것은 아닙니다. 특히 Google Sheets의 기존 5개 논리 구상에 현재의 작업 내역을 어떻게 저장할지는 아직 결정해야 합니다. [미해결 질문](03_OPEN_QUESTIONS.md)이 서비스 개발의 핵심 맥락입니다.
