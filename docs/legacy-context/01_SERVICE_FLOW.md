# 서비스 흐름과 구성 요소의 역할

이 문서는 서비스가 해야 할 일을 설명합니다. 아래 전 과정이 구현됐다는 뜻은 아닙니다.

## 역할 분담

| 구성 요소 | 맡을 역할 | 현재 확인된 상태 |
|---|---|---|
| 원본 서비스 | 요청·작업·자료·검토 등의 근거를 보관 | UI 예시에 출처명만 있으며 실제 연결 없음 |
| 연결 수단 | 허용된 계정·범위의 기록과 메타데이터를 조회 | 서비스별 접근·조회·쓰기 지원 검증 필요 |
| LLM | 프로젝트·태스크·작업 내역의 관계를 이해하고 연결·정리·갱신 판단 | 미구현 |
| 팀 공통 데이터 허브 | 현재 업무 관계·요약·검토·변경 근거를 지속 보관. 기본 방향은 Google Sheets | 실제 시트 연결·운영 스키마 미구현 |
| 조회·검토 화면 | 팀 현황·개인별 내역·근거 탐색, 필요한 판단 | 가상 데이터 UI 구현 |

화면 제공에 Sites를 사용하는 방향이 논의됐지만, 현재 파일은 독립 TypeScript/CSS 프로토타입입니다. 배포 환경에서 연결 기능을 실제로 실행할 수 있는지는 확인해야 합니다.

## 업무 기록이 현황으로 바뀌는 흐름

```text
접근 가능한 원본 기록 확인
    → 원본 ID·작성자·발생 시각·확인 시각·출처 정리
    → 기존 프로젝트·태스크·자료 연결과 비교
    → 기존 태스크의 새 근거인가, 새 작업 내역인가, 별도 태스크인가 판단
    → 명확한 연결·정리와 확인이 필요한 판단 분리
    → 허용된 변경 반영 또는 검토 요청
    → 변경 전후·근거·판단자·실행 결과 보관
    → 공통 데이터를 읽어 화면 갱신
```

원본이 하나 늘었다고 반드시 태스크나 작업 내역이 하나 늘어나는 것은 아닙니다. 요청을 보낸 것, 실제로 작업한 것, 검토한 것, 전달한 것, 태스크가 완료된 것은 서로 다른 사실일 수 있습니다.

## LLM과 저장 실행의 경계

LLM은 근거와 함께 연결·변경을 판단해야 합니다. LLM이 작성한 문장 자체를 사실이나 저장 성공으로 취급하지 않습니다. 저장 단계에서는 대상 ID, 허용 필드, 현재값, 권한, 필요한 승인과 중복 여부를 확인해야 합니다. 이 검증 단계와 실제 실행 주체는 아직 구현되지 않았습니다.

## 갱신 실행

사용자가 같은 기록을 반복 입력·분류하지 않아도 되게 하는 것이 목표입니다. 어떤 서비스는 어떤 범위를 자동으로 읽을 수 있는지, 어떤 트리거·주기로 실행할 수 있는지 아직 확인이 필요합니다. 실제 지원이 확인되지 않은 자동 실행을 약속하거나, 매번 수동 수집하는 흐름을 완성된 해결책으로 취급하지 않습니다.

실패·권한 부족·불확실성을 기존 확정 정보를 지우는 근거로 사용하지 않습니다. 갱신하지 못한 상태와 실제 업무가 변경된 상태를 구분해야 합니다.
