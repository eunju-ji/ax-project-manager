# 데이터·동일 업무 판단·원본 근거

## 저장해야 할 정보와 확정되지 않은 스키마

Google Sheets에는 Projects / Tasks / Sources / Reviews / History라는 5개 논리 구상이 있습니다. 현재 서비스는 프로젝트 → 태스크 → 작업 내역을 구분하므로 **작업 내역의 독립 식별·저장·자료 연결**을 이 구상에 맞춰야 합니다.

아래는 관리해야 할 의미 단위입니다. 시트 개수, 열 이름, 별도 테이블 여부를 새로 확정한 설계가 아닙니다.

| 의미 단위 | 필요한 정보 |
|---|---|
| 프로젝트 | 안정적인 ID, 목적과 범위, 태스크 관계, 현재 설명 |
| 태스크 | 안정적인 ID, 프로젝트 관계, 목적·완료 기준·담당자·업무 유형 |
| 작업 내역 | 안정적인 ID, 태스크 관계, 실제 실행자·기록 시각·수행 내용·자료 관계 |
| 원본 자료/기록 | 서비스·계정 범위·원본 ID·원본 링크·작성자·발생 시각·확인 시각 |
| 업무와 원본의 연결 | 어느 업무를 어떤 역할로 뒷받침하는지, 연결 근거와 확인 상태 |
| 검토 | 판단 대상, 제안 내용, 근거, 검토자, 판단과 적용 결과 |
| 변경 이력 | 대상, 변경 전후, 근거 원본, 판단 주체와 실제 적용 시각 |

프로젝트·태스크·작업 내역의 ID는 행 번호나 화면 순서로 대체하지 않습니다. 원본을 식별하는 키와 업무에 연결하는 관계의 키는 구분해야 합니다.

## 같은 업무인지 판단

예를 들어 Drive의 화면 시안, GitHub의 구현 커밋, Chat의 검토 요청은 하나의 태스크에 연결될 수 있습니다. 그러나 같은 사람이 작성했거나 제목이 비슷하다는 이유만으로 하나로 합치면 안 됩니다.

판단 근거에는 명시적 태스크 ID·원본 참조, 프로젝트 목적, 기대 작업물, 완료 기준, 요청 흐름, 기존 자료 관계가 포함됩니다. 판단 규칙·자동 처리 기준은 미해결이며, 모호한 관계를 확정 사실로 저장하지 않는 것이 원칙입니다.

메일 작성자는 요청자일 수 있고 실제 실행자는 다른 사람일 수 있습니다. LLM이 요약을 작성한 일과 사람이 수행한 업무도 구분합니다. 확인되지 않은 실행자를 추측으로 채우지 않습니다.

## 중복과 다대다 관계

- 같은 원본을 다시 조회하는 것은 새 업무가 아닙니다.
- 여러 원본이 한 태스크를 설명할 수 있습니다.
- 같은 자료가 여러 태스크의 근거가 될 수도 있습니다.
- 원본 생성·수정·조회 시각과 실제 작업 시각은 다를 수 있습니다.
- 원본 변경을 반영하는 것과 새 작업 내역을 추가하는 것의 기준은 정해야 합니다.

서비스·계정 범위·원본 ID를 이용한 안정적인 원본 키를 고려합니다. 중복 수집 방지와 동일 업무 판단은 별개 문제입니다. 태스크를 찾는 의미 판단과 같은 파일을 두 번 저장하지 않는 식별 검사를 혼동하지 않습니다.

## 원본이 이동·삭제·접근 불가가 된 경우

이미 수행한 업무가 사라지면 안 됩니다. 원본 파일의 현재 이용 가능성과 과거 업무의 존재는 별도로 관리해야 합니다.

안정적인 원본 ID와 연결 관계를 유지하고, 단순 접근 실패·권한 변경·확인된 삭제를 구분해야 합니다. 마지막으로 확인한 시각과 보존이 허용된 제목·출처·작성자·요약·결정 정보 등이 맥락 유지에 필요할 수 있습니다.

**어떤 내용을 얼마 동안 보존할지, 권한이 바뀐 뒤 어디까지 보여줄지는 아직 정해야 합니다.** 과거에 접근 가능했다는 이유로 원문 전문이나 미리보기를 계속 공개할 수 있다고 가정하지 않습니다. 업무 이력 보존과 원문 노출 범위를 분리합니다.

## 팀 공통 정보와 권한

공통 저장소에는 팀이 공유할 수 있는 업무 현황과 근거 관계를 보관합니다. 원본의 세부 내용은 원본 서비스의 권한을 따릅니다. 개인 연결 계정으로 읽은 내용을 다른 사람에게 어디까지 공유할지, 공통 데이터를 실제로 쓰는 계정은 무엇인지 정해야 합니다.

## 변경과 이력의 일관성

Google Sheets는 참조 관계·여러 행 변경·동시 갱신을 자동 보장하는 관계형 DB가 아닙니다. 읽은 뒤 다른 사람이 수정한 경우, 작업 내역만 저장되고 자료 연결은 실패한 경우, 재시도로 같은 변경이 중복된 경우를 처리해야 합니다.

쓰기 전 현재값 확인, 적용 결과 재조회, 변경 ID·실행 ID·근거 관계, 부분 실패 구분 등이 설계 논점입니다. 구체적인 저장 계약과 충돌 처리 방식은 아직 확정되지 않았습니다.
