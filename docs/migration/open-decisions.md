## OD-01. 대상 범위
- A. AX팀 파일럿만 / B. AX팀 파일럿, 전사 확장 가능한 모델 / C. 처음부터 전사
- **권고 B**(N02 D-01과 같음). 확장성을 이유로 구조를 키우지 않는다(P8).
- **파일럿 범위 승인은 실사용자 데이터 접근 승인이 아니다.** 데이터 접근은 OD-13 G2에서 따로 승인한다.

## OD-02. 리소스 단위 — MVP 범위 조정
- Legacy: 화면은 **작업 내역 건수**이며 시간·가동률이 아니라고 명시(L04, L05).
- 신규: 계획/확인/잔여 **공수(시간)** 비교가 MVP·성공 기준·백로그에 들어 있다(N01 §6·§8, N05, DEV-03).
- A. 건수만 / B. MVP는 건수, 공수는 사람이 입력·확인하는 별도 기록으로 후속 / C. 처음부터 공수
- **권고 B.** 이벤트 수로 시간을 추정하지 않는다(D-08, Q10)는 데 양쪽이 동의한다.
- **B 채택 시 함께 바뀌는 것**(승인 대상):
  - N01 §6 MVP의 "확인 공수", §8 "계획 대비 투입/잔여 공수" → 후속으로 이동
  - N05 파일럿 목표 "담당자별 계획/확인 공수와 잔여 예상 공수 구분" → 후속으로 이동
  - 백로그 DES-02·DEV-03 → "건수 기반 현황 + 공수는 후속"으로 재정의
  - N05 "허용된 데이터 소스 2개 이상 연계 시연"은 **유지**(OD-05에서 1개로 줄이지 않음)
- 건수 MVP에서 검증할 의사결정: "누가 어느 프로젝트·업무 유형에 참여하고 있는가", "확인 요청이 어디에 쌓였는가".
- 명시할 한계: 작업 내역 1건의 규모 차이, 공동 작업(권고: 실행자마다 1건, 팀 합계는 고유 WorkLog), 실행 시각 기준 주 집계(미상이면 별도 표시).

## OD-03. 업무 계층
- A. 프로젝트>태스크>작업 내역 + 업무 유형 5종 속성(legacy, UI 구현됨)
- B. Project>Workstream>Task>Activity(신규 초안)
- C. A에 선택적 Workstream 추가
- **권고 A.** UI·테스트가 이미 A를 전제로 한다. 신규 초안의 Activity(발생 이벤트)는 **계층이 아니라 근거 쪽의 엔터티**로 다룬다(OD-04). Workstream이 필요한 실제 사례가 나오면 C로 확장.

## OD-04. 논리 저장 구조
- Legacy 5개 논리 구상(Projects/Tasks/Sources/Reviews/History)에는 **작업 내역**과 **업무-근거 연결**이 빠져 있다.
- **권고 논리 엔터티(방향안)**: Project, Task, WorkLog(작업 내역), Source(원본 객체, 키 = 서비스+계정 범위+원본 ID), **SourceEvent(발생 이벤트·버전)**, Link(업무 ↔ 근거, 역할·근거·확인 상태, 다대다), Review, History, AccessAudit. 공수(Effort)는 OD-02 B 채택 시 후속.
- **이벤트 보존 계약(필수)**: 같은 원본의 서로 다른 변경·회의·메시지를 구별할 수 있게 이벤트 식별자, 발생 시각, 수집(조회) 시각, 실행자(확인/미상 구분)를 보존한다. SourceEvent를 별도 엔터티로 둘지 Source의 버전 행으로 둘지는 M1 설계에서 결정.
- 원본 객체 ≠ 발생 이벤트 ≠ 작업 내역. 이벤트가 WorkLog가 되는지는 OD-14 판단의 결과다.
- ID는 행 번호·화면 순서와 무관한 불변 ID. 원본 식별 키와 관계 키를 분리한다.
- **M2 PoC 전에 정할 쓰기 계약의 기대 결과**: 재시도해도 같은 변경이 한 번만 적용(실행 ID 멱등성), 읽은 뒤 다른 쪽이 수정했으면 덮어쓰지 않고 충돌로 표시, WorkLog·Link·History 중 일부만 저장되면 감지·표시. 물리 구현 상세는 OD-09 뒤.
- 화면 JSON은 운영 스키마가 아니며 어댑터 출력 형식으로만 유지. 다대다 투영 한계는 `ui-reuse-plan.md` §4 참조.

## OD-05. 첫 연동 소스
- 신규 초안: Drive·Calendar 우선. Legacy 예시: Drive·Gmail·Chat·GitHub(Calendar 배제 아님). 우선순위 미합의.
- **권고**: M1에서 `ax-integration-research`로 Drive·Calendar·GitHub·Chat의 공식 API 읽기 범위·최소 권한·변경 감지 방식을 **문서 조사만** 하고(실데이터 접근 없음), 파일럿 목표인 **2개 이상**을 선정. Drive는 양쪽 공통이라 1순위 후보.

## OD-06. AI 대화(ChatGPT·Claude)
- 전체 대화 자동 접근이 지원된다는 증거 없음(L03 Q01).
- A. 원문 자동 수집 시도 / B. 원문 수집 제외, 사용자가 선택한 요약·산출물 링크만 / C. 공식 Export 파일 업로드
- **권고 B**, C는 공식 제공 범위 조사 후 선택. "수동 내보내기"를 자동 수집이라고 표현하지 않는다(P2).

## OD-07. 완료 판단과 승인
- 현재 UI: 태스크 판단 영역에서 "맞아요·완료 / 아니요·진행 중" 선택(메모리 상태).
- **권고(단일안)**: LLM은 근거와 함께 완료 **제안**만 한다. 담당자가 판단(완료 제안)하고 **프로젝트 책임자가 확정**한다. 판단자·시각·변경 전후·근거를 History에 남기고, 화면은 "판단함"과 "저장 성공/실패"를 구분해 표시한다.
- 함께 정할 예외(M1 설계에서 상태 전이 계약으로 확정, M2 영속화 PoC 전 필수):
  - 담당자 = 책임자(자기 승인): 허용하되 History에 표시
  - 책임자 부재: 대리 확정자 지정 방식
  - 재판단: 완료 → 진행 중 되돌리기 허용, 이력 보존
  - 동시 판단: 나중 쓰기가 덮어쓰지 않고 충돌로 표시(OD-04 계약)

## OD-08. 권한·보존·노출·감사
- **지금 승인할 원칙**:
  - 원문뿐 아니라 제목·작성자·요약·History의 변경 전후 값도 보호 대상이다. History가 과거 민감정보를 계속 노출하는 경로가 되지 않게 한다.
  - 공통 현황 / 보존 메타 / 요약 / History 각각에 대해 열람·보존·삭제 범위를 정한다.
  - 공통 데이터 접근 감사(AccessAudit)를 둔다.
  - 사람별 리소스 지표를 감시·성과 평가 근거로 쓰지 않는다는 목적 제한과 사용자 고지(N01 §7)를 승계한다.
- 연동 착수 전(G2) 정할 세부: 개인 계정으로 읽은 내용의 팀 공유 범위, 공통 허브 쓰기 계정(서비스 계정 vs 개인), 보존 기간, 권한 상실 시 숨길 항목.

## OD-09. 실행 환경·물리 저장소
- 후보: (A) Google Sheets + Apps Script/Sites(legacy 방향, P8) / (B) Sheets를 허브로 두고 경량 백엔드가 연동·검증 수행 / (C) 별도 DB + 웹앱. N04는 개념 모델이며 특정 저장소를 정하지 않았다.
- Sheets 한계: 참조 무결성·다중 행 트랜잭션·동시성 미보장(L02).
- **권고**: M1 연동 조사 결과를 반영해 후보를 좁히고, OD-13 게이트에 맞춰 PoC로 비교(OD-04 쓰기 계약 기대 결과, 권한 적용, 트리거 가능 여부). Q11(연결 기능이 화면/백그라운드에서 실제로 동작하는가)이 핵심 기준.

### OD-09 전환 기준 (사용자 지시, 2026-11-19)
- 로컬 PoC(M2-L)의 쓰기 계약 결함 수정이 **3회차에도 Sheets식 제약 때문에** 통과하지 못하면 (A) Sheets 단독 운영을 후보에서 내리고 (B)·(C)를 우선 검토한다.
- 판단 방법: 회차마다 실패 원인을 "저장소 제약(여러 행 원자적 저장 불가, 행 잠금 부재 등)"과 "구현 결함"으로 분류해 기록한다. 저장소 제약으로 분류된 실패가 남으면 전환 근거로 쓴다.
- 대안 비교 시 관점: 트랜잭션 지원, 동시 쓰기 직렬화, 팀이 Sheets로 현황을 보는 경험 유지 방법(예: DB가 원본이고 Sheets는 읽기 전용 내보내기), 운영 부담·비용(유료 인프라는 AGENTS §9 승인 대상).

## OD-14. 동일 업무 판별 기준 (Q03)
- 새로 들어온 근거를 **기존 태스크의 추가 근거 / 기존 태스크의 새 작업 내역 / 새 태스크** 중 무엇으로 볼지 판별하는 기준.
- 권고 방향: 명시적 태스크 ID·원본 참조가 있으면 우선, 없으면 LLM 후보 + 근거 제시 → 사람 확정. 이름이 비슷하거나 작성자가 같다는 이유만으로 병합하지 않는다(L02).
- **교정 지속성**: 사용자가 거절·재연결한 판단은 다음 수집에서 같은 오판이 다시 적용되지 않아야 한다.

## OD-15. 자동 처리 vs 검토 경계 (Q07)
- 권고 방향: 자동 허용 목록(예: 같은 원본 재수집 식별, 명시적 ID가 있는 연결, 요약 문구 갱신)만 자동, 나머지(모호한 연결, 병합, 완료, 근거 충돌)는 검토 필수.
- 근거가 충돌하면 후보를 모두 근거와 함께 보여주고 확정하지 않는다.

## 제안 MVP 우선순위 (승인 전, 구현 착수 아님)
1. **M0 UI 기준선 확보 (G0)**: 빌드 재현(V1)·시각 스냅샷(V2)·키보드 체크(V3), 생성물 추적 정리(OD-12).
2. **M1 설계 + 연동 문서 조사 (G0)**: 논리 모델·이벤트 보존·최소 쓰기 계약 기대 결과(OD-04), 완료 상태 전이(OD-07), 판별·자동 경계(OD-14·15)를 ADR로. 병행해 연동 문서 조사(OD-05). 합성 데이터 픽스처와 어댑터 계약 테스트.
3. **M2 실행 환경 PoC (G0 → 필요 시 G1 승인)**: OD-09 후보 비교. 합성 데이터로 검토 판단 영속화 + History + 멱등성·충돌·부분 실패 + **LLM 연결 제안·사람 교정**까지 검증.
4. **M3 제한적 시험 연동 (G2 승인 후)**: 선정 소스 2개 이상, 시험 사용자만.
5. **M4 파일럿 → 운영 판단 (G3)**.
6. 후속: 공수 기록(OD-02 B), Workstream(OD-03 C), 추가 소스.
