1. 한눈에 보기

AX 프로젝트 관리장은 팀원이 따로 기록하지 않아도 Drive·Chat·Gmail·GitHub·AI 작업 세션에 이미 남은 흔적을 읽어 "누가, 어떤 프로젝트의 어떤 일을, 언제 했는지"를 자동으로 정리하는 도구다. 사람은 정말 판단하기 어려운 것만 본다.

11프로젝트 (WBS에 없는 프로젝트 포함)
50태스크 (완료 26)
61작업 내역
187근거 자료 (파일·메시지·커밋·AI 세션)
7종수집 출처
하루 4회정기 수집 (09·12·15·18시)
핵심 네 가지
  1. 업무 구조는 프로젝트 › 태스크 › 작업 내역 세 단계다. 태스크는 "끝났다고 말할 수 있는 일"이다.
  2. 시스템이 먼저 판단한다. 프로젝트·태스크를 세우는 것부터 완료까지, 근거가 분명하면 자동으로 반영한다. WBS에 없어도 마찬가지다.
  3. 업무만 기록한다. 회의 초대·파일 이동 같은 기록은 숨기지 않고 아예 남기지 않는다.
  4. 원문은 저장하지 않는다. 내용은 읽되 이름·시각과 160자 이하 요약만 남긴다.

2. 무엇을 생각하며 만들었나

만들면서 계속 붙든 질문과, 그 질문에 대해 지금까지 내린 답이다. 사용자의 지적으로 답이 바뀐 것도 그대로 적었다.

고민지금의 답왜
사람이 기록하지 않아도 되게 하려면?이미 남는 흔적(Drive·Chat·메일·커밋·AI 세션)을 읽어 시스템이 프로젝트·태스크·작업 내역을 세운다. 근거가 분명하면 완료까지 자동으로 바꾼다.입력을 요구하는 도구는 결국 비게 된다.
무엇을 "업무"로 볼 것인가?무언가를 만들고, 분석·검토·결정하고, 문제를 해결한 기록만. 파일 이동·회의 초대·자료 재공유·질문만 한 AI 대화는 남기지 않는다.흔적이 있다고 다 일은 아니다. 섞이면 요약과 진척이 틀어진다.
프로젝트·태스크를 무엇으로 가를까?WBS가 아니라 일의 실체로. 태스크는 "끝났다고 말할 수 있는 일", 프로젝트는 목표를 향해 여러 날 이어지는 일의 묶음. WBS는 있으면 쓰는 계획 정보다.회의에서 나온 과제처럼 WBS에 없는 일이 실제로 많다.
얼마나 잘게 나눌까?같은 목적·같은 결과물로 이어지면 한 태스크. 요청·메일 대응·후속 수정은 그 태스크의 작업 내역.잘게 쪼개면 맥락이 사라진다.
완료와 지연을 어떻게 판단할까?산출물을 열어 결과가 채워졌으면 완료. 기한이 지났는데 작업이 있으면 지연, 작업도 근거도 없으면 확인 필요. 완료일은 결과가 갖춰진 날.계획 날짜만 보면 이미 끝난 일도 지연으로 뜬다.
회사 정보를 어떻게 지킬까?원문은 읽기만 하고 저장하지 않는다(이름·시각·160자 요약). 실데이터는 Git 밖 전용 폴더. 빼 달라는 것은 이력까지 지운다(purge).도구가 정보 유출 경로가 되면 안 된다.
잘못 판단하면?모든 변경을 delta 한 경로로만, 이력과 함께 남긴다. 사람이 고친 값은 자동으로 덮지 않는다.되돌릴 수 있어야 자동화를 믿을 수 있다.
AI로 한 일은 누구의 일인가?Paseo로 Claude·GPT 에이전트에게 시킨 일은 시킨 사람의 작업 내역. 세션은 근거로 붙는다.지금 팀의 개발·분석 상당 부분이 에이전트를 통해 이뤄진다.
화면은 어떻게 보여야 하나?일반 웹서비스처럼 라벨만. 설명 문구·시스템 정보·내부 분류 용어를 드러내지 않고, 한국 웹서비스에서 흔한 말을 쓴다.사용자는 시스템이 아니라 일을 보고 싶어 한다.
혼자 쓰던 것을 팀이 쓰려면?공개 사이트에 회사 Google 계정 + 초대제 로그인, 역할별 권한. 수집은 연결이 있는 사용자 PC에 두고 결과만 토큰으로 올린다.Workspace 연결과 AI 세션 기록은 그 PC에 있고, 열람은 통제되어야 한다.

방향을 바꾼 지점

처음 생각바꾼 기준이유
시스템이 제안, 사람이 확정근거가 분명하면 시스템이 바로 반영(완료 포함)사람 확인을 기다리면 기록이 늘 밀린다.
Drive 메타데이터만 수집Drive·Chat·Gmail 내용까지 읽고 요약만 저장같은 업무가 여러 곳에 있을 때 묶으려면 내용이 필요하다.
WBS 유무로 업무를 나눠 표시태스크·프로젝트 여부를 WBS로 가르지 않는다업무는 WBS가 있을 수도 없을 수도 있다.
프로젝트는 WBS 대분류에서만작업 공간·목표 문서·여러 날 작업 등이 겹치면 시스템이 프로젝트를 세운다회의에서 나온 과제(예: 사내 지식 구축)는 WBS에 없지만 분명한 프로젝트다.
요청 하나하나를 태스크로같은 목적·결과물로 이어지는 일은 한 태스크너무 잘게 쪼개면 맥락이 안 보인다.
Drive 변화가 있으면 작업 내역만들고·분석·검토·결정·해결한 기록만파일 이동·회의 초대·일정 취소는 업무가 아니다.
업무 아닌 기록은 "참고 기록"으로 숨김아예 남기지 않음기록하는 것은 "업무"다.
지운 기록도 이력에 원래 값 보존요청 시 이력 내용까지 지우는 purge특정 프로젝트를 빼 달라는 요청은 사본도 남기지 말라는 뜻이다.
AI 대화는 수집 대상 아님Claude Code·Codex 세션과 내보내기 파일을 색인만 해서 연결AI 에이전트로 하는 개발·분석도 실제 업무다.
내 PC에서만 실행공개 사이트에서 사람마다 로그인·권한팀이 함께 보고 쓰려면 접근 통제가 있는 사이트가 필요하다.

8. 판별 규칙

프로젝트인가 신규

하나의 목표와 결과물을 향해 여러 날 이어지는 일의 묶음이면 프로젝트다. 아래 신호가 두 가지 이상 겹치면 시스템이 세운다(ADR-021).

신호예
전용 작업 공간로컬 작업 폴더, Paseo 워크스페이스, Git 저장소, Drive 폴더, Chat 스페이스
목표를 적은 문서README·PLAN·기획서·회의록에 목적·범위·완료 기준
이틀 이상 이어진 작업같은 주제의 커밋·AI 세션·파일 수정이 다른 날에도 있음
회의·지시에서 나온 과제"~를 구축하자"로 정해진 일
계획 문서WBS·업무계획의 대분류
  • 목표로 이름 짓는다. "Paseo 작업"이 아니라 "사내 지식 구축".
  • 같은 목표의 작업 공간이 여럿이면(로컬 폴더 + 나중의 GitHub 저장소) 한 프로젝트로 묶고, 대응을 수집 설정(projects_map)에 남겨 다음 판별에 쓴다.
예: 사내 지식 구축회사 안의 지식을 AI가 쓰기 좋은 형태(온톨로지·지식 데이터)로 만드는 프로젝트. WBS에는 없지만 전용 작업 폴더, 계획 문서, 이틀 이상 이어진 Paseo(Claude Code·Codex) 작업이 겹쳐 프로젝트로 세웠다. 첫 태스크는 "OCR·문서 파서 실험실 구축". GitHub에 연결하면 저장소가 같은 프로젝트에 더해진다.

태스크인가

태스크

끝낼 수 있는 일. 목표·결과물이 있고 누가 해야 하는지 말할 수 있다.

예: 결과서 작성, 실험실 구축, 이관, 결과가 남는 리뷰

태스크 아님 → 기록하지 않음

  • 정보·사례 공유
  • 업무일지·주간보고
  • WBS·업무계획 갱신 그 자체
  • 회의 일정 조율·초대
  • 참고 자료 모으기
  • 같은 목적·결과물로 이어지는 일은 한 태스크. 개별 요청·메일 대응·후속 수정은 작업 내역이다.
  • 애매하면 "이 일이 끝났다고 말할 수 있는가"로 가르고, 그래도 애매하면 판단 보류(notes)로 남긴다.

9. 공개 사이트·인증 신규

로그인

  • Google 로그인(OpenID Connect, PKCE)
  • 회사 도메인 계정 + 이메일 인증된 계정만
  • 초대된 사람만 입장, 첫 관리자는 설정값으로 지정
  • 로컬 개발은 127.0.0.1에서만 로그인 생략 가능

세션·보안

  • 서버 저장 세션, HttpOnly·Secure 쿠키, 유휴 12시간·최대 7일
  • 상태 변경 요청은 Origin 확인 + CSRF 토큰
  • 보안 헤더(CSP·HSTS 등), 로그인 시도 제한
  • 로그인·조회·권한 변경·업로드를 접근 감사에 기록
역할할 수 있는 일
관리자사람 초대·역할 변경·비활성화, 모든 화면, 검토 결정, 수집 토큰 발급·폐기
구성원팀 화면 보기, 검토 결정·정정
보기팀 화면 보기만
  • 로그인 계정은 데이터의 사람과 이메일로 연결되어, 화면의 담당자가 곧 그 계정이다.
  • 파일럿은 초대된 사람이 팀 데이터를 모두 본다. 프로젝트별 공개 범위는 후속.
  • 사용자 PC의 수집기는 push-delta로 수집 토큰을 붙여 판별 결과를 올린다. 서버는 같은 apply-delta 규칙으로 반영한다.
보안 검토 (11/24, AX-Reviewer)차단 등급 문제는 없었다. 중요 3건을 고친 뒤 재검토를 통과했다: 보기 권한 사용자가 로그아웃되지 않던 문제, 인코딩된 주소로 운영 모드의 데이터 차단을 우회하던 문제, 프록시 뒤에서 모든 사용자가 로그인 시도 제한을 함께 쓰던 문제.
배포 전 결정할 것호스팅 위치(클라우드 / 사내 서버 / 인트라넷), 도메인, 회사 Google OAuth 클라이언트 등록(내부 사용자 유형), 첫 관리자. 컨테이너 이미지와 배포 절차서는 준비하고, 실제 배포는 승인 게이트(G3) 뒤에 한다.

  • 데이터 출처·수집 시각·판별 주체 같은 시스템 정보는 보이지 않는다.
  • WBS 유무 같은 내부 분류를 화면에 드러내지 않는다.
  • 한국 웹서비스에서 흔한 말을 쓴다.
  • 간트 바는 계획 기간, 점은 실제 작업한 날(지금 방식 유지).
