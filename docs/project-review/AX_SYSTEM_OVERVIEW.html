AX 프로젝트 관리장 — 구조와 판단 기준 정리

지금까지 고민하고 정한 내용, 시스템 구조, 데이터 구성, 자동 판별 규칙을 한 곳에 모은 문서

작성AX-Lead 기준일2026-11-23 버전1.0 단계M4 실데이터 파일럿 운영 상태운영 중

1. 한눈에 보기

AX 프로젝트 관리장은 팀원이 따로 기록하지 않아도 Drive·Chat·Gmail에 이미 남은 흔적을 읽어 "누가, 어떤 프로젝트의 어떤 일을, 언제 했는지"를 자동으로 정리하는 도구다. 사람은 정말 판단하기 어려운 것만 본다.

핵심 세 가지
  1. 업무 구조는 프로젝트 › 태스크 › 작업 내역 세 단계다. 태스크는 "끝났다고 말할 수 있는 일"이다.
  2. 시스템이 먼저 판단한다. 근거가 분명하면 연결·완료까지 자동으로 반영하고, 애매한 것만 남긴다.
  3. 원문은 저장하지 않는다. 내용은 읽되 이름과 160자 이하 요약만 남긴다.

2. 무엇을 풀려고 하나

문제

  • 업무 기록이 Drive·Chat·메일·WBS에 흩어져 있다.
  • 진척을 보려면 사람이 따로 정리해야 하고, 정리는 늘 늦다.
  • 같은 일이 여러 곳에 다른 이름으로 남아 하나로 보기 어렵다.

목표

  • 흩어진 기록을 같은 업무 단위로 묶는다(통합 취합).
  • WBS 계획과 실제 작업을 한 화면에서 비교한다.
  • 사람의 입력 부담을 거의 없앤다(자동 판별 우선).

파일럿은 AX팀(공유 드라이브 AX_TF, 관련 Chat 스페이스, 메일)으로 시작했다. 모델은 다른 팀으로 넓힐 수 있게 만든다(ADR-001).

방향을 바꾼 지점

처음 설계와 달라진 부분이다. 같은 실수를 반복하지 않도록 이유와 함께 남긴다.

처음 생각바꾼 기준이유
시스템이 제안하고 사람이 확정근거가 분명하면 시스템이 바로 반영(완료 포함)사람 확인을 기다리면 기록이 늘 밀린다. 명확히 끝난 것은 1차로 시스템이 판단한다.
Drive 메타데이터만 수집Drive·Chat·Gmail 내용까지 읽고 요약만 저장메타데이터만으로는 같은 업무가 여러 곳에 있을 때 묶을 수 없다.
WBS에 있는 일과 없는 일을 나눠 표시태스크 여부는 WBS로 가르지 않는다업무는 WBS가 있을 수도 없을 수도 있다. "WBS에 없는 업무", "계획 외 업무" 같은 구분은 쓰지 않는다.
요청·메일 대응 하나하나를 태스크로같은 목적·결과물로 이어지는 일은 한 태스크너무 잘게 쪼개면 맥락이 안 보인다. 개별 요청은 그 태스크의 작업 내역이다.
Drive에 변화가 있으면 작업 내역만들고·분석·검토·결정·해결한 기록만 작업 내역파일 이동, 회의 초대, 일정 취소는 업무가 아니다.
업무 아닌 기록은 "참고 기록"으로 숨김업무 아닌 기록은 아예 남기지 않음우리가 기록하는 것은 "업무"다. 숨긴 묶음은 무엇인지 알 수 없는 데이터만 늘린다.
WBS 업무 카테고리를 업무 유형으로 사용업무 유형은 ADR-003의 5종만둘을 섞었더니 요약 숫자와 유형별 분포가 맞지 않았다.
계획 기간이 지나면 모두 지연지연(작업 있음)과 확인 필요(작업·근거 없음)를 구분, 산출물로 완료 자동 판별결과서가 이미 있는데 지연으로 뜨는 오판이 많았다.

  • 프로젝트: 목적이 있는 일의 묶음

6. 판별 규칙

태스크인가 아닌가

태스크

끝낼 수 있는 일. 목표나 결과물(완료 상태)이 있고 누가 해야 하는지 말할 수 있다.

예: 결과서 작성, 대시보드 개발, 이관, 결과가 남는 리뷰 회의

태스크 아님 → 기록하지 않음

  • 정보·사례·도구 공유
  • 업무일지·주간보고·개인 체크리스트
  • WBS·업무계획 갱신 그 자체
  • 회의 일정 조율·초대·채널 운영
  • 참고 자료 모으기
  • WBS 여부로 가르지 않는다. WBS 행은 태스크로 들이되, WBS에 없다고 태스크가 아닌 것은 아니다.
  • 단위: 같은 목적·같은 결과물로 이어지는 일은 한 태스크. 요청·메일 대응·후속 수정은 그 태스크의 작업 내역이다.
  • 새로 만들기 전에 같은 프로젝트의 기존 태스크에 넣을 수 있는지 먼저 본다(이름·폴더·파일명·참여자·시기·명시적 참조).
  • 애매하면 "이 일이 끝났다고 말할 수 있는가"로 가르고, 그래도 애매하면 만들지 않고 notes에 남긴다.

완료·지연·확인 필요

stateDiagram-v2
  direction LR
  [*] --> 예정: 시작일 전
  [*] --> 일정미정: 계획 기간 없음
  예정 --> 진행중: 시작일 지남
  진행중 --> 완료: 산출물·완료 근거 확인
  진행중 --> 지연: 종료일 지남 + 작업 내역 있음
  진행중 --> 확인필요: 종료일 지남 + 작업·근거 없음
  지연 --> 완료: 산출물 확인
  확인필요 --> 완료: 근거 발견
  일정미정 --> 완료: 완료 근거 확인
상태조건
완료결과물이 채워져 있거나 끝났다는 분명한 근거가 있다. 산출물 기반 자동 완료: 시작일이 지난 미완료 태스크마다 산출물에 맞는 파일을 찾아 내용을 읽고, 양식만 있으면 그대로 두고 결과가 채워져 있으면 사람 확인 없이 완료 처리한다.
지연종료일이 지났고, 작업 내역은 있지만 완료 근거가 없다.
확인 필요종료일이 지났는데 작업 내역도 근거도 없다. 시스템이 판단할 재료가 없으니 사람이 본다.
진행 중시작일이 지났고 종료일 전이다(또는 종료일 없이 작업 중).
예정 · 일정 미정시작일 전 / 계획 기간이 없다. 시작일만 있으면 "~ 종료일 미정"으로 표시.
완료일 정하는 법결과가 갖춰진 작업 내역의 시각을 완료일로 쓴다. 계획 종료일이나 수집 시각을 완료일로 쓰지 않는다. 예: 계획이 11/16이어도 결과 보고서를 11/13에 작성했다면 완료일은 11/13.

프로젝트 기간: 태스크 계획 기간과 작업 내역 중 가장 이른 날부터 가장 늦은 날까지. 기록을 거슬러 수집하면(백필) 시작일이 앞당겨진다.

7. 화면 원칙

구성

  • 업무 요약: 일간·주간·월간, 사람별 탭
  • 작업 내역 히트맵: 날짜를 누르면 그날 요약으로 이동
  • 프로젝트 WBS 간트: WBS 묶음 행, 상태 칩, 계획 기간 바, 작업한 날(파란 점)
  • 태스크 드로어: 오른쪽에 업무 설명·속성·날짜별 작업 내역
  • 자료 창: 폴더 전체 파일 목록, 해당 파일 2초 연한 강조, 파일 행 누르면 파일, 아래 "Google Drive에서 폴더 열기"

문구 원칙

  • 일반 웹서비스처럼 라벨만 둔다. 설명 문구를 붙이지 않는다.
  • 데이터 출처·수집 시각·판별 주체 같은 시스템 정보는 보이지 않는다.
  • 내부 분류(WBS 유무, 계획 외 등)를 화면 문구로 드러내지 않는다.
  • 번역투·조어 대신 한국 웹서비스에서 흔한 말을 쓴다(적음/많음, 최근 순, 확인 필요).
간트 바와 파란 점바는 WBS 계획 기간, 파란 점은 실제 작업한 날이다. 계획보다 일찍 하거나 늦게 하면 둘이 떨어져 보인다. 이 표시 방식은 그대로 유지하기로 했다(2026-11-23).

8. 보안·운영 원칙

원칙내용

범위1:1 Chat 제외, AI 대화 원문 자동 수집 제외.

10. 용어
